# Agents Manager — Design & MVP

A local, terminal-native manager for **workstreams**: units of work that span one or more repos, each backed by
exactly one Claude Code conversation, with worktrees, status and cleanup handled for you.

Assumptions: everything runs locally on macOS, Terminal.app, Claude Code CLI with a Claude subscription (no API keys).

## Pain points

1. Work is tied to terminal tabs; closing a tab = losing the thread.
2. One task spanning several repos ends up as several unrelated Claude conversations.
3. Worktrees are manual and accumulate as a graveyard.
4. No overview of "what am I working on, which session needs me, where is each PR".

## Design decisions

| # | Decision |
|---|----------|
| D1 | **Workstream is the primary unit.** Name + N (repo, branch) pairs + exactly **one** Claude session. All context lives in one conversation. |
| D2 | **Sessions run in a manager-owned tmux server** (`tmux -L agentmgr`), running the real interactive `claude` CLI (subscription auth). Closing a terminal never kills a session. |
| D3 | **All CLI/TUI, no web app, no daemon.** The dashboard is a TUI living in the same tmux server as the sessions; you switch between dashboard and sessions with a keystroke in one Terminal window. Hooks and commands write straight to SQLite. |
| D4 | **The manager creates worktrees, not Claude.** `claude --worktree` only isolates the repo it's launched in; for multi-repo we `git worktree add` each repo into the workstream folder and launch Claude at its root. |
| D5 | **Workstream folder layout**: Claude's cwd is the workstream folder, repos are subfolders (see below). |
| D6 | **Workstream brief is a generated `CLAUDE.md`** at the workstream root: repos, branches, rules, cleanup expectations. |
| D7 | **Cleanup is owned by the manager**, with safety checks. Claude is told the rules but never removes worktrees. |
| D8 | **Everything is resumable.** Session UUID fixed at creation (`--session-id`); if tmux dies, `claude --resume <id>`. |
| D9 | **"Needs you" status comes from Claude Code hooks**, not screen scraping. |
| D10 | **PR status comes from `gh`**, polled per (repo, branch). |
| D11 | **No cross-workstream coordination.** Collisions are rare; resolved by rebase at merge time. |
| D12 | **Every workstream has a key, a name and optionally a ticket ID.** Key = stable folder name (`PROJ-313` if given to `wm new`, else `WS-<n>`). Name = 3 words, chosen by Claude at intake. Ticket ID (e.g. `PROJ-313`) can be given at `wm new` or mentioned during intake. Branches are `<ticket-or-key>-<name-slug>`, e.g. `proj-313-dark-mode-toggle`. |
| D13 | **Constraints are enforced, not just instructed**: the manager does all structural work itself, Claude Code permissions + a `PreToolUse` guard hook block violations, a `PostToolUse` check detects drift. See "Guardrails". |
| D14 | **Workstreams start with a voice/text intake in their own session**: Claude writes `TASK.md` and attaches repos via `wm add-repo`, confirms, then works. |

```
~/workstreams/WS-7/                       ← claude cwd, never renamed (outside ~/code on purpose, see Guardrails)
    CLAUDE.md                             ← generated by the manager (D6)
    TASK.md                               ← the brief, written by Claude at intake (D14)
    .claude/settings.json                 ← generated: permissions + hooks (D9, D13)
    acme-web/                             ← git worktree, branch proj-313-dark-mode-toggle
    acme-api/                             ← git worktree, branch proj-313-dark-mode-toggle
~/workstreams/PROJ-313-dark-mode-toggle → WS-7   ← convenience symlink, updated when name/ticket is set
```

### Why no web app (D3)

Everything the MVP needs works well in a terminal: a live list, fuzzy autocomplete, status, jumping into a
session. Staying inside tmux removes the HTTP server, the frontend, and the AppleScript "open terminal" dance —
"open" becomes `tmux switch-client`. Attention while you're elsewhere comes from the tmux status line and macOS
notifications. The core (state, git, tmux, gh) is a library, so a web UI can be added later if a Linear board
needs one.

## MVP

### UX

One entry point: `wm` (name TBD).

- `wm` → attaches the current Terminal window to the manager tmux server, on the **dashboard**.
- Dashboard (TUI):
  ```
  WORKSTREAMS                                           ⚠ 2 need you
  ⚠ PROJ-313 Dark mode toggle   waiting: permission (Bash)   3m   acme-web     PR #412 open ✓ checks
                                                                acme-api     no PR · 2 unpushed
  ● PROJ-320 Search fix         working                      1m   acme-web     PR #409 draft ✗ checks
  ◐ PROJ-301 CSV export         your turn                   22m   release-t.   PR #88 merged → archive?
  ○ WS-4     Old spike          stopped                      2d   acme-api     no PR · clean
  ```
  Sorted: needs-you first, then working, your-turn, stopped.
  Keys: `enter` open session · `n` new · `a` add repo · `r` resume · `b` rebase · `x` archive · `p` refresh PRs · `q` detach.
- Inside a session: `C-b h` returns to the dashboard; `C-b n` jumps to the next session that needs you
  (tmux prefix keys, because Claude Code already uses many Ctrl keys, e.g. `C-g` opens the editor). Status line always shows the workstream name and `⚠ N need you`.
- Scriptable commands, same functionality: `wm new`, `wm ls`, `wm open <ws>`, `wm add-repo`, `wm archive`,
  `wm resume`, `wm repos`, `wm branches`, `wm doctor`.

### User stories

1. **Create.** `wm new` (no arguments) → you land in a fresh Claude session and describe the task by voice (or
   text), naming the repos and optionally the ticket. Claude picks a 3-word name, writes `TASK.md`, attaches the
   repos via `wm add-repo` (the manager creates the worktrees and branches), reads back a summary, and starts
   after you confirm. See "Workstream startup".
2. **Overview.** Dashboard: status, repos, branches, git state (dirty / unpushed / behind), PR state, age.
3. **Needs you.** When a session is blocked (permission prompt, question) or finishes its turn, it's flagged
   in the dashboard and status line; a macOS notification fires if you're not currently looking at that session.
4. **Open.** `enter` / `wm open <ws>` switches to the session.
5. **Resume.** Stopped session (reboot, crash) → `r` relaunches `claude --resume <id>`.
6. **Adopt work in progress.** `wm add-repo <key> <repo> --adopt` moves an existing branch and/or uncommitted
   changes from a normal checkout into the workstream: stash, free the branch in the source checkout (main checkout
   → default branch, other worktree → detached HEAD), create the worktree, apply the changes. Rolled back on failure.
   Git only; earlier Claude conversations are not carried over.
6b. **Add a repo mid-work.** New worktree inside the folder, `CLAUDE.md` updated; the running session sees it.
7. **PR status.** Per repo: none / draft / open (checks ✓✗…, review state) / merged / closed.
   All repos merged → the workstream is suggested for archive.
8. **Archive.** Dry-run report per repo (uncommitted, unpushed, merged?). Refuses if work would be lost unless
   forced. Then kill session, `git worktree remove`, optionally delete merged branches, mark archived.

### Session status (D9)

`wm` writes hooks into the workstream's `.claude/settings.json`; each runs `wm hook <event>`, which reads the
hook JSON from stdin (has `session_id`, `cwd`) and updates SQLite.

| Hook | State |
|------|-------|
| `SessionStart` | `your turn` (fresh or resumed session waits for input) |
| `UserPromptSubmit` | `working` |
| `PreToolUse` / `PostToolUse` | `working` (flips back after a permission is granted) |
| `Notification` (permission prompt / elicitation) | `needs you` + reason, notify |
| `Stop` | `your turn`, notify |
| `SessionEnd` / tmux session missing | `stopped` |

"Needs you" = blocked mid-task (highest priority). "Your turn" = Claude finished and waits. Notification is
skipped if a tmux client is currently viewing that session.

### Base freshness

Only `origin/<default>` is fetched (`git fetch origin +refs/heads/main:refs/remotes/origin/main`, 20s timeout,
repos in parallel): from the dashboard when a repo's last fetch is older than 5 minutes (checked every 30s; `p`
forces it), and in the `SessionStart` hook if older than 60s (5s timeout). The last attempt, last success and error
are stored per repo (`fetches` table). The dashboard shows "N behind base" while unmerged (yellow from 20), "fetch failed", and
"origin checked Xm ago". Nothing is ever merged or rebased automatically.

### Rebase on request

`b` / `wm rebase` fetches origin and shows a plan per repo, then rebases each branch that is behind its base. Skipped:
merged PRs, wrong branch, an operation in progress, uncommitted changes, and commits on `origin/<branch>` that aren't
local (rebasing would drop them). Refused while Claude is working or waiting on a prompt, so the tree doesn't change
under it. A branch already on origin is pushed with `--force-with-lease=<branch>:<sha seen in the plan>`, so a push
made by someone else after the plan is never overwritten. A conflicting rebase is aborted (`git rebase --abort`), and
one message listing the repos and files is typed into the Claude session (`tmux send-keys`), or passed as the initial
prompt when resuming a stopped session; Claude resolves, tests and pushes.

### PR status (D10)

`gh pr list --repo <remote> --head <branch> --state all --json number,state,isDraft,reviewDecision,statusCheckRollup,url`,
cached in SQLite, refreshed every ~60s while the dashboard is open and on demand. If `gh` isn't authenticated,
show "PR: n/a" instead of failing. MVP doesn't create PRs; Claude does that via `gh` when asked.

The Git column shows one state per repo, from git plus the cached PR (`view.git_state`, first match wins):
broken (worktree missing, wrong branch, rebase/merge in progress) → merged (leftover uncommitted work or commits after
the PR head, CI on the base branch failing/running, else `✓ merged`) → already in base → PR closed → local work
(uncommitted, needs push, no changes yet, needs PR) → open PR (draft, CI failing, conflicts, changes requested, CI
running, needs update from base, awaiting review, blocked by branch rules, else `● ready to merge`). Local work beats
the open PR's state because the PR's checks are then about an older commit. Squash merges leave the branch "unpushed"
and "behind", so those counts are ignored once the PR is merged.

Only the PR whose head is the workstream branch is tracked, but work often reaches base through other branches: the
last PR of a stack, a re-cut branch, a cherry-pick. So git decides too: if merging the branch into base would change
nothing (`git merge-tree --write-tree base HEAD` equals base's tree, `gitops.in_base`), the repo is `✓ already in base`
whatever its own PR says. It then counts as merged for archiving, and `wm rebase` skips it.

### Workstream startup: voice intake, then work

Creating a workstream is a conversation, in the same Claude session that will do the work (D1).

```
$ wm new                  # no arguments; you land in the Claude session of workstream WS-7
> (voice) "We need a dark mode toggle in the web app — it's PROJ-313. The preference is saved by
   the API, so that repo needs a new setting, and the web UI needs the toggle. Done when …"
Claude: wm set WS-7 --name "dark mode toggle" --ticket PROJ-313
        writes TASK.md
        wm add-repo WS-7 acme-api ; wm add-repo WS-7 acme-web
        → "PROJ-313 · dark mode toggle. Goal … Repos: acme-api, acme-web on
           proj-313-dark-mode-toggle. Done when … Go?"
> "go"
Claude: starts working
```

**Phase 1 — the manager creates an empty workstream** (`wm new [TICKET] [--repo …] ["task text"]`, all optional):

1. Allocate the key: the ticket ID if given (validated `^[A-Z][A-Z0-9]*-\d+$`, not already active), else `WS-<n>`.
2. Create `~/workstreams/<key>/`. The key never changes afterwards: the folder is the session's cwd, and Claude
   Code files conversations by cwd, so renaming it would break `--resume`.
3. Generate `CLAUDE.md` + `.claude/settings.json`; start `claude --session-id <uuid>` in tmux session `<key>`.
4. Dashboard shows it as `intake` until it has a name, a `TASK.md` and at least one repo.

With `--repo` and task text, intake is shortened (Claude still names it and writes `TASK.md`, but repos are
already attached).

**Phase 2 — intake (Claude, guided by `CLAUDE.md`)**. When `TASK.md` doesn't exist yet, Claude must:

1. Listen to the description (voice or typed). Ask at most a couple of clarifying questions.
2. **Name it**: `wm set <key> --name "<3 words>" [--ticket PROJ-313]`. The name is a 3-word summary
   (lowercase, e.g. "dark mode toggle"); the ticket only if you mentioned one. The manager updates the status line
   and the convenience symlink; the folder and tmux session stay `<key>`.
3. Write `TASK.md` (format below).
4. **Attach repos**: `wm add-repo <key> <repo> [--branch <existing>]`. The manager creates the worktree and the
   branch `<ticket-or-key>-<name-slug>` from the repo's default branch, so the naming stays guaranteed.
   It refuses until a name is set (the branch depends on it). Voice transcription mangles names
   ("acme ML pipeline"), so `CLAUDE.md` lists the available repos and `add-repo` fuzzy-matches, rejecting
   anything ambiguous with the candidates. `wm set <key>` and `wm add-repo <key>` are pre-approved via `--allowedTools` on the `claude` command line
   (not in settings.json: project-level allow rules make Claude Code re-ask for folder trust).
5. Read back a short summary (name, ticket, goal, repos + branches, done-when, open questions) and **wait for
   confirmation**. Transcription and repo matching can be wrong; one "go" is cheap. Corrections at this point are
   cheap too: `wm set` again, `wm remove-repo` (only allowed while the worktree has no commits).
6. Then start working. `set` / `add-repo` regenerate `CLAUDE.md`, so identity and the repo table are current.

**`TASK.md` — the brief** (owned by you + Claude; `CLAUDE.md` is manager-owned and regenerated):

```markdown
---
key: WS-7
ticket: PROJ-313
name: dark mode toggle
---
## Goal
## Context            (what you said, cleaned up — keep your wording where it matters)
## Done when          (checkable acceptance criteria)
## Out of scope
## Open questions
## Decisions & progress   (Claude appends at milestones: what changed, where, why)
```

- Name, ticket and repos are authoritative in the DB (set via `wm set` / `wm add-repo`); the frontmatter mirrors them.
- `CLAUDE.md` imports it with `@TASK.md`, so the brief is always in context, survives compaction and is
  re-read on resume.
- "Decisions & progress" makes resuming after days away (and a future Linear sync) trivial.
- It's a plain file in the workstream folder (not in a repo): readable, editable, archived with the workstream.

**Context channels**

| Channel | Content | Why this channel |
|---|---|---|
| `CLAUDE.md` (generated) | Identity, intake procedure, available repos, attached repos/branches, rules, `@TASK.md` | Loaded every session, re-applied after compaction and on resume |
| `TASK.md` | Goal, done-when, decisions | The brief; written during intake, living afterwards |
| `.claude/settings.json` (generated) | Permissions, guard + status hooks | Enforcement, not persuasion |
| Shared memory (`~/.agents-manager/memory/`) | How the user likes to work, feedback, references: anything that applies to every task | Claude's auto memory is per folder, so per workstream by default; `wm` passes `--settings '{"autoMemoryDirectory": …}'` so every workstream shares one. `CLAUDE.md` says what belongs there (task facts go in `TASK.md`, repo facts in the repo's `CLAUDE.md`) |
| `SessionStart` hook output | *Live* state: branch, dirty/ahead/behind, PR per repo | Fresh on every start/resume |

**Generated `CLAUDE.md`** (sketch):

```markdown
# Workstream WS-7 · PROJ-313 · dark mode toggle

@TASK.md

## Intake (only while TASK.md does not exist)
The user will describe the task, often by voice, possibly mentioning a ticket like PROJ-313. Then:
1. `wm set WS-7 --name "<3-word summary>" [--ticket <ID>]`
2. write TASK.md (see format)
3. `wm add-repo WS-7 <repo>` for each repo mentioned
4. summarise name / goal / repos / done-when, and wait for confirmation before changing any code.
Available repos: acme-web, acme-ml-pipeline, acme-api, release-tools, …

## Repos
| Folder    | Repo     | Branch                    | Base        |
|-----------|----------|---------------------------|-------------|
| acme-web/ | acme-web | proj-313-dark-mode-toggle | origin/main |
| acme-api/ | acme-api | proj-313-dark-mode-toggle | origin/main |

## Rules
- Only modify files inside these subfolders (and TASK.md). ~/code checkouts are read-only reference.
- Never create, remove or move git worktrees, never switch branches. Guard hooks enforce this;
  if a command is blocked, read the reason and adjust.
- Need another repo? `wm add-repo WS-7 <repo>`.
- Commit per repo; mention the ticket (PROJ-313) in commits and PR titles (`gh pr create` when asked).
- Append to "Decisions & progress" in TASK.md at meaningful milestones.

## Done means
- Every "Done when" item in TASK.md checked; everything committed and pushed in every repo.
- Don't clean up worktrees or branches — the manager archives the workstream.
```

Each repo's own `CLAUDE.md` is still loaded when Claude works in that subfolder. Repo-level
`.claude/settings.json` / `.mcp.json` do **not** apply (only the cwd's do) — accepted MVP gap.

### Guardrails (D13)

Layered, from strongest to weakest:

| Constraint | Guaranteed by | Strength |
|---|---|---|
| Worktree exists, folder + branch carry the ID | Manager creates them; Claude isn't asked to | **Guaranteed** |
| No edits outside the workstream folder (Edit/Write/NotebookEdit tools) | `permissions.deny: ["Edit(~/code/**)"]` + guard hook rejects any `file_path` outside the folder, except the shared memory folder and Claude's scratchpad for this workstream (symlinks resolved) | **Enforced** |
| No Claude-created worktrees | `permissions.deny: ["EnterWorktree"]`; guard hook denies subagents launched with worktree isolation | **Enforced** |
| No `git worktree …`, `git checkout/switch <branch>`, `cd`/`git -C` into `~/code/<repo>` via Bash | Guard hook on `Bash` parses the command, denies with a reason Claude can act on | **Best-effort** (Bash can always be obfuscated) |
| Worktrees still on their branch, no new worktrees in the repos | `PostToolUse` check after every Bash call: compares `git branch --show-current` and `git worktree list` with the DB; on drift, tells Claude to revert and flags `⚠ drift` in the dashboard | **Detected** within one tool call |
| All of the above at OS level | Claude Code's Bash sandbox with writes limited to the workstream folder + each repo's `.git` (worktree commits write objects there) | **Opt-in** (`wm new --sandbox`); adds network-permission friction, so not the default |

Why `~/workstreams` instead of `~/code/.workstreams`: deny rules win over allow rules, so `Edit(~/code/**)` could
not be denied if the workstreams also lived under `~/code`.

The guard hook's denial reason is shown to Claude (e.g. *"Blocked: `git checkout main` would switch the branch of
worktree acme-web. Stay on proj-313-dark-mode-toggle; use `git show main:path` to read other branches."*),
so a violation turns into a correction rather than a dead end.

### Architecture

Single Python package (installed with `uv tool install`), no long-running process:

- **TUI**: Textual. **CLI**: Typer. **Fuzzy pickers**: inside Textual (and for `wm new` prompts).
- **State**: SQLite (WAL) at `~/.agents-manager/state.db` — workstreams, repos, session id, status, PR cache.
  Written concurrently by hooks and the TUI.
- **Git / tmux / gh**: subprocess wrappers.
- **tmux server** `-L agentmgr` with its own config `~/.agents-manager/tmux.conf` (user's tmux untouched):
  - session `home` runs the dashboard; one session per workstream, named by its key (`WS-7`); the status line shows ticket + name.
  - `mouse on`, big `history-limit`, drag-select → `pbcopy` (Terminal.app lacks OSC 52).
  - key bindings for dashboard / next-needs-you; `status-right` runs `wm status-line`.
- **Notifications**: `osascript -e 'display notification …'`.

### Done when

- Create a two-repo workstream with fuzzy branch selection in < 30s, landing inside the Claude session.
- Close all Terminal windows; `wm` brings back the dashboard with all sessions alive.
- A permission prompt in a background session shows `⚠` in the status line within ~1s and notifies.
- PR state per repo is visible and correct (draft/open/checks/merged).
- After a reboot, `r` restores the same conversation.
- Archive removes worktrees and refuses when there is unpushed or uncommitted work.
- Main checkouts in `~/code/<repo>` are never modified.

### Not in the MVP

Linear, web UI, last-message previews, collision detection, MCP tools, multiple sessions per workstream,
merging repo-level Claude settings, PR creation by the manager, remote/cloud.

## Later (rough priority)

1. **Last-message preview** in the dashboard from the transcript (`transcript_path` from hooks).
2. **Linear**: create a workstream from an issue (name, branch, brief pre-filled); issue state in the dashboard;
   minimal writes (In Progress, PR link). Possibly the trigger for a web board view.
3. **Merge repo settings**: each repo's `.claude/settings.json` / `.mcp.json` into the workstream's.
4. **Collision badge**: `git merge-tree --write-tree` between active branches of the same repo (informational).
5. launchd / login auto-start, other terminals (iTerm2 `-CC`, Ghostty).
